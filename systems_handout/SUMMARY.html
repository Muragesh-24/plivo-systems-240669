Low-Latency 20-of-32 Erasure Coding

This implementation ensures the reliable delivery of a 50 FPS real-time stream across a highly degraded UDP network. It strictly adheres to the 2.0x bandwidth multiplier constraint and is built entirely using standard C++17 and POSIX sockets.

This architecture is entirely unidirectional. Frames are encoded and dispatched the moment they are generated. The receiver rebuilds and forwards the frame immediately upon collecting enough shards. This allows the harness player to handle final deadline scheduling without the receiver introducing any artificial buffering delays.

Network Protocol

The standard 160-byte payload is fractured into twenty distinct 8-byte chunks. The sender processes these as coefficients of a degree-19 polynomial in GF(256), evaluating them across 32 unique nonzero field points. Due to Vandermonde matrix properties, retrieving any 20 of these 32 evaluated points guarantees full reconstruction of the original 160 bytes.

Over the wire, packets are precisely 10 bytes long. A 2-byte big-endian header allocates 5 bits for the shard identifier and 11 bits for the frame sequence. This sequence field loops every 2,048 frames, cleanly supporting over 40 seconds of continuous 50 Hz traffic.

For a standard 30-second run (1,500 frames), the overhead calculation mathematically guarantees compliance with the bandwidth cap:

(1500 frames × 32 shards × 10 bytes) / (1500 frames × 160 bytes) = Exactly 2.00000x.

Receiver Logic & Decoding

The receiving service allocates an expected frame tracker, which holds memory and a bitmask for the 32 potential shards. Because of this structure, UDP out-of-order delivery is natively resolved, and redundant shard IDs are ignored. Once the 20th unique datagram arrives for a given frame, the software builds a 20x20 matrix and applies Gauss-Jordan elimination over GF(256) to retrieve the raw payload.

Once pushed to the player, a boolean flag is set to discard any excessively delayed duplicates. The code handles all network-to-host byte order translations, validates lengths, and runs on an event-driven loop to prevent blocking execution.

Architectural Decisions

Network Problem Engineering Solution
Random Packet Loss The system can survive the total erasure of up to 12 datagrams per frame.
Dense Burst Drops By distributing frames into tiny, independent shards, a burst drop only degrades part of the frame, easily absorbed by the 12-shard parity margin.
Severe Jitter & Reordering Arrival sequence does not matter; decoding begins the instant any 20 shards are collected.
Latency Overhead Unidirectional FEC completely removes the round-trip time required by ARQ (retransmission) models.
Strict Bandwidth Cap Bit-packing the header into exactly 2 bytes maxes out the 2.0x allowance without violating the rules.

Final Performance & Limits

Target Playback Delay: 71 ms.

During final grading runs on Profile B, tests evaluated at 71 ms recorded miss rates of only 0.73% and 0.53% across different seeds, while consuming precisely 2.0x bandwidth. Attempts to tighten the delay to 70 ms resulted in failures above the 1% threshold. The architecture also easily cleared Profile A (35 ms delay) with a 0.60% miss rate.

The only remaining failure vectors for this system are extreme latency spikes exceeding 71 ms, or profound network outages that destroy more than 40% (13+ shards) of a single frame's transmission. Furthermore, because the frame counter is 11 bits, streams lasting longer than 2,047 frames are unsupported by design.
